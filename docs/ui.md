# The UI: `drafftink-ui`

`drafftink-ui` (L6) is the egui user interface. It is thin: it reads the command registry and the session, builds actions, and the actions end in `Session::execute_from(origin, id, args)`. It holds no document logic. The rules are in `AGENTS.md`; the commands are in `docs/commands.md`; how a shell uses a session is in `docs/engine.md` section 4.

## 1. The shape of a frame

```
Session ──refresh──> Model (snapshot) ──draw──> Vec<UiAction> ──dispatch──> Session::execute_from
                                  ^                  ^
                      keymap::resolve_keys ──────────┘   (key events become the same actions)
```

* `Model` (`model.rs`) is a snapshot: every command with its title, shortcuts and `available` result (the refusal text), the tool, the selection count, the style of the selection, the common bounds, the selected elements (kind, link, frame, label), the camera, the library while its panel is open, settings, tabs, history labels. The reads go through `Session::query`, which runs a `reads_only` command (`style.get`, `selection.get`, `element.query`, `view.get`, `library.list`, and `library.thumbnail` through `Model::read_thumbnails`) and leaves no ring entry; the crate does not use `drafftink-edit` any more (it still uses `drafftink-scene` for the colour palette and the document name). `Model::refresh(&mut Session)` recaptures only when a cheap stamp over the session changed. `Session::query` needs `&mut self`, so the model's readers take `&mut Session` and the thin test checks that they call only `query` and never `execute*`.
* `draw(ui, &Model, &mut UiState) -> Vec<UiAction>` draws every surface. It has no session in its signature.
* `UiShell::frame(ui, &mut Session, FrameInput)` is what an app calls once per egui pass: refresh, resolve keys, draw, then `dispatch`. It returns a `FrameResult` with the commands that ran (and what they returned), the requests for the app (`HostRequest`), and whether a modal dialog is open (pointer events must not reach the canvas then).
* The UI returns **all** actions of a frame in order. The old `render_ui` returned the first one and dropped the rest.

## 2. Action routing

`action.rs` has the whole routing story.

| Action | Meaning | Goes to |
|---|---|---|
| `UiAction::Command(Call { id, args, origin })` | run a registered command | `Session::execute_from` |
| `UiAction::Scrub(Scrub { phase, command, args })` | one step of a dragged control (the opacity and corner radius sliders and the custom colour picker, docs/exceptions.md E13) | `gesture.begin` / `gesture.update` / `gesture.end` / `gesture.cancel` through `execute_from`; the gesture id is remembered in `UiState` |
| `UiAction::Verb(Verb)` | open or close UI (docs/commands.md §6.3) | `UiState::apply_verb` |
| `UiAction::Host(HostRequest)` | something only the app can do: file pickers, clipboard text, a link | returned to the app in `Report.host` |

The verbs are the 29 of docs/commands.md §6.3 (`ui.open_color_picker` and `ui.pick_color` count once more for the brush colour of the paint editor) (the last one, `ui.open_about`, is the About dialog with the source offer, `surfaces/about.rs`). This work added `ui.open_export`, `ui.open_preferences`, `ui.toggle_library`, `ui.toggle_versions` and `ui.rename_document`; `ui.save_as` now opens a name dialog first. `ui.toggle_debug` is the debug panel (section 5d). The minimap (section 5e) is not a verb: it is the setting `view.minimap`, switched through `settings.toggle` like the snap and attach switches.

`route(&UiAction, &UiState) -> Routed` is the one function that decides this. `dispatch(sink, state, actions, now)` executes in order. `CommandSink` is implemented by `Session`; tests use a recording sink. Origins: `ui` for buttons, `menu`, `context_menu`, `palette` and `shortcut` for the other surfaces. The origin is recorded in the ring and never changes a result.

Refusals: any refusal becomes a toast with the text unchanged (plus a button for the first `suggest` entry). Three cases are handled differently: a refusal that comes from a shortcut with the code `no_target`, `nothing_to_do` or `not_applicable` is silent (`QUIET_FROM_KEYBOARD`); `unsaved_changes` opens a confirm dialog that re-runs the call with `on_unsaved` set; `no_save_target` asks the app for a save picker.

Controls (`widgets.rs`): every control that does something is `Cx::command_widget` underneath. It looks the command up in the model, greys out when `available` refuses and shows the refusal text as the tooltip, names itself for accessibility from the binding title (`Rectangle tool`) or the command title, and pushes the call on a click. A command the registry does not have (a build without it) is greyed with "`x` is not available in this build." and cannot run. Every catalog command is registered now, so the tests build that case with `Fixture::without(&["x"])`. A property that does not apply to the selection is greyed with the engine's reason for it: `style.get` reports it per property (`reason`, the words `style.set` refuses with), and `Ctl::blocked` carries it.

The UI has no refusal text of its own (`tests/refusals.rs`). A control is greyed, not hidden (the context menu is the exception, see `menu_kit.rs` below; so are the groups of the strip, see below), and its tooltip is the engine's text: the availability of its command (`Model::refusal_text`), the `reason` of `style.get`, or, for a dialog choice that is not a command, the engine's own words for the thing (the refusal of a command that needs a selection; the description of the `doc.export` argument). A condition that only the run can check (a count, a kind) leaves the control enabled, and the refusal comes back as a toast with the same text the bridge returns. Where a command can answer from the selection alone, it does: `default_targets` of `frame.unwrap`, `frame.select_children`, `frame.remove`, `text.wrap_in_container` and `arrow.edit_points` runs the same check as `execute`, so a panel control is greyed with that text, and the context menu leaves the row out (`tests/context_menu_rows.rs`). The `element.convert` targets depend on the kinds, `text.bind` and `text.unbind` name the text and the container, and the frame rename dialog needs the frame, so those rows are built from the selection. "Copy as text" is always listed because the check needs the `format` argument; the engine refuses at the click ("none of the elements holds text"). The ribbon leaves a group out when `style.get` says its property applies to no selected element (a rectangle has no heads, no font) or when the engine refuses its command (align needs two elements, distribute three: `arrange.align` and `arrange.distribute`), and greys a control with the engine's reason when it applies to some of them. Every refusal of a `gesture.*` command is a toast, except `no_gesture`, which only means that the drag had already ended. `doc.export` to a file that cannot be written is a refusal (`io_failed`, "did NOT happen"), so the export dialog stays open with the reason; a write that the port finishes later (`pending_write`) leaves the dialog open with a note. Exporting a picture has one path: the menu row "Export as PNG", `Mod+E` and the palette row run the call of the dialog for an export at once (`surfaces::export::complete_args` fills the `to` download named after the document, the scope and the look from the `export.*` settings for every call of a command whose registration says `completes_export`; what the call gave stays). Without `to` the command answers inline, which is for agents. The refusal of such an export is a toast also from the keyboard (`nothing_to_do` and `no_target` are quiet for other shortcuts), so `Mod+E` on an empty drawing says why nothing happened.

Menus (`menu_kit.rs`): the context menu, the hamburger menu and the tab menu are lists of calls on `Menu` (`command`, `verb`, `host`, `local`, `submenu`, `grid`, `separator`, `heading`), drawn with one row painter at one width (`MENU_WIDTH`). A row has the fixed height of the layout, a 16 px icon slot (which holds the check mark of a toggle), the label, the shortcut dimmed at the right and a chevron when it opens a flyout. The label of a command row is `Model::label(id, args)`: the title of the binding or the `Variant` (`CommandSpec::variants`, a named call without keys) that fixes those arguments, else the command title, so a command reads the same in the menus, the panel and the palette (`context_menu_rows::every_label_is_the_title_the_registry_gives_the_call`). A flyout opens beside its row, flips to the left at the window edge, stays inside the window, and closes 0.25 s after the pointer rests on another row of the menu. The keyboard uses egui's focus: Up and Down move, Right opens a flyout, Left closes it, Enter runs a row, Esc closes the menu; a `grid` of cells (the arrowheads) takes all four arrows inside it and hands Up and Down to the rows around it at its edges; while a popup menu is open the keymap leaves the arrow keys and Enter to it. A menu is a `Role::Menu` node with a name ("Context menu", "Main menu", "Tab menu", the flyout's name), which is how the tests find its rows.

Nothing mutates session state from a widget. `crates/ui/tests/thin.rs` reads the crate source and fails when: a file other than `shell.rs`, `model.rs` or `action.rs` names `Session`; `&mut Session` appears outside the shell and the sink; any call that changes state is used (`tab_mut`, `set_raw`, `queue_write`, the `gesture_*` methods, `SceneTx`, ...); an `execute*` name other than `execute`, `execute_from`, `execute_batch` appears; or the model reads something from the session that is not on the read list.

**Geometry.** No surface knows the height of another as a number. `chrome::ChromeRects` (in `UiState::chrome`, reset at the start of every `draw`) holds the rectangle of each surface that takes room, recorded when it is drawn; `surfaces::show_all` draws in the order of dependencies (strip, bottom bar, tabs, then the panels, popovers, toasts and the stats panel, which read the rectangles). The tool column stays centred on the window and scrolls when it would reach the strip (`scroll_when_taller`); the strip is two rows tall, so on a window of 800 points or less the column scrolls. A group that must be measured before it is placed (the strip's groups, a column that may scroll) is laid out first in a hidden sizing pass.

**Tokens.** `theme/tokens.rs` has the type scale (`TextSize`), the spacing scale (`space`), the radius ladder (`radius`) and the control heights (`Control`, with the touch heights). A surface asks for `TextSize::Body`, not `13.0`; `tests/tokens.rs` fails on a new literal font size in `surfaces/`. The UI font is the `ui.font` setting (`theme::UiFontChoice`); headings that keep GelPen use `TextSize::hand`.

The strip has an image group for one selected image: a first row with "Crop image" ("Done cropping" while the crop editor is open) and "Edit picture" (`image.paint_begin`, the icon is a picture with a brush), over a second row with "Reset crop" (only while the image is cropped) and "Reset paint" (`image.reset_paint`, only while it has paint). Their labels are the registry titles. The context menu (and so the long press on touch) has the same rows ("Crop image", "Reset crop", "Edit picture", "Reset paint").

**The paint editor in the strip** (`surfaces/brush.rs`, `surfaces/ribbon/paint.rs`). While the editor is open (`Model::paint_editing`, from `observed.paint_editor`) the strip shows the brush and nothing of the style of the selection: the stroke, fill, width, corner, opacity, layering and action groups would only change the outline of the image, so `ribbon::shows` says no to every property and the one group is `Group::Paint`. The colour group changes places with the brush colours: the first row has the label "Brush", the six quick colours, the colour last picked, the eyedropper and the wheel; the second row has "Mode" with the two buttons "Paint" and "Erase". Next to it the "Edit picture" group has two rows: the size slider (a log scale from 1 to 400 picture pixels, with its value in px) and the hardness slider, then the opacity slider, Reset (`image.reset_paint`, greyed with the engine's words while the image has no paint) and Done (`image.paint_end`, a check mark filled with the accent). Each slider has a small picture in front of it (a dot beside a circle, a disc with a soft edge, a half-filled disc), named by its tooltip and accessible name ("Brush size", "Brush hardness", "Brush opacity"). Every control is one command: the mode buttons and the swatches are `image.paint_brush` with a `mode` or a `color`, and never `style.set`. A slider calls `image.paint_brush` at each step of a drag and is not a scrub of docs/exceptions.md E13: the brush is session state with no undo step to share, so there is no gesture to wrap it in, and the command is quiet in the ring. On a narrow window the same rules as for the other groups apply: the colour button of the strip holds a swatch of the brush colour and opens a popover with the swatches, the eyedropper and the mode, and the "Edit picture" group waits behind "More" in a row of finger-sized controls that fits the menu (tested at 390 points).

**The colour of the brush is not mapped for the dark theme** (`ColorTarget::Brush`, `ColorTarget::is_themed`). The brush paints pixels of a picture, and the canvas draws pictures as they are, so the swatches show the colour as stored and a pick stores it as it is: the eyedropper's pixel is the brush colour in both themes, where a stroke or fill pick stores the inverse of the dark mapping (`colors::stored`). The eyedropper reads the scene texture as it does for the stroke, so it samples the picture itself: the veil of the editor lies under the edited picture, not over it, and the picture is drawn in its own colours. A pick over the dimmed rest of the canvas returns the dimmed pixel, as every pick returns the canvas as drawn.

**What the canvas shows** (`app/src/view.rs`, `app.rs`). The app leaves the edited image out of the scene, draws a translucent veil over the rest of the canvas (`Theme::paint_veil`, the page colour of the theme at 60 %, in `drafftink_render::fill_veil`) when `PaintView::veil` is set, and then composes `PaintView::shown` (the image with the draft stroke on it) on top, the way the crop editor composes its picture, so the image keeps its crop, rotation, mirroring and corner radius. Over the picture the OS cursor is a crosshair at the middle of the brush ring (`InteractionOverlay::eraser`); off the picture, where there is no ring and a click ends the editor, the canvas's own cursor shows. A pen or a finger takes the same pointer path.

Look and feel is the old app's: floating cards with a 1 px border, soft shadow, 8 px radius and 12 px margins, the accent blue `#3b82f6` for the active tool, tab and primary button, GelPen for headings (the bytes come from `drafftink_typeset::font_file`, so the binary holds each font file once), the three canvas font families shown in their own faces in the font picker. Icons are drawn with the egui painter (`icons.rs`): no SVG assets, no image loader. All colours come from `theme::Palette`; the dark palette is chosen by the egui theme, which follows the `theme` setting (`light`, `dark`, `system`). Zen mode hides the chrome and keeps dialogs and toasts.

### Colours the UI shows

The canvas draws stored element colours through the dark mapping in the dark theme (`render.md`, "Dark theme"), so
the UI never shows a stored colour as it is: `colors.rs` is the one place that applies `Color::for_dark_theme` and its
inverse `Color::from_dark_theme` (the same functions as the renderer, no second copy). In the light theme both are
the identity and nothing below changes.

* **Swatches show the display.** The quick swatches of the top strip, the last-picked
  swatch, the cells of the colour popover (grid and quick column) and the page-colour button show
  `for_dark_theme(stored)`. A palette cell is a stored colour: a pick sends the palette name as before
  (`style.set {stroke_color: "blue-500"}`), so the document holds the same colour in both themes and a light-theme
  viewer sees the intended one. The swatch is exactly the colour of the line that gets drawn.
* **Colours named by their look store the inverse.** The Black and White cells of the quick column, and a colour
  typed in the hex field, mean "this colour on screen": the pick stores `from_dark_theme(seen)` and the swatch shows
  what that draws. In the dark theme White stores `#010001` and is drawn `#eeedee`, the lightest the dark canvas has.
  A colour the filter cannot show is stored as the one whose display is nearest; the swatch shows that display.
* **The ring** (which swatch is current) compares stored colours, so it is the same in both themes.
* Not recoloured: peer cursors and user colours (`collab.rs`), the accent and the chrome (`theme::Palette`).

Tests: `tests/color_popover.rs` reads the circle painted for each swatch (dark: every grid cell equals
`for_dark_theme(palette colour)`, picks store the palette colour or the inverse, the top bar, the last-picked swatch
and the page button follow) and `app/tests/app.rs` compares the swatch with the colour the painter encodes.

The palette lists a row per titled binding and one per other palette command, with the first shortcut and, for a refused command, the refusal text inline. A command with required arguments and no binding that fixes them opens a form generated from its JSON Schema (`args_form.rs`; enum, boolean, number, string, `Option`, raw JSON fallback with an inline error). The shortcuts dialog is generated from `keymap::help_rows`, which reads the registry, so it cannot go stale (the old list had 19 stale entries).

## 4. Keymap

Shortcuts are data on the registrations (`Binding`). `keymap::resolve_keys(events, &KeyContext) -> Vec<UiAction>` is the only key dispatcher.

* `Mod` is Cmd on macOS and Ctrl elsewhere (`egui::Modifiers::command` is Ctrl on Linux and Windows, Cmd on macOS). `Ctrl` means the physical Control key on macOS.
* Letters without Alt match the logical key (AZERTY users get the letters they see). Digits, punctuation and every chord with Alt match the physical key, named by its US layout. `?` and `+` are typed with Shift and match the logical key, so Shift is implied.
* Scope order: `Text`, `PointEditor`, `Canvas`, `Always`. `PointEditor` applies only while the line or arrow point editor has a selected point, so `Delete` means `arrow.delete_point` there and `element.delete` otherwise. During a text edit only `Text` and `Always` chords apply, plus `Mod` chords of commands with the `Commit` gate (docs/commands.md §6.2). While a modal dialog is open only `Always` applies.
* Nothing is handled while an egui text field has focus (`egui_wants_keyboard_input`). Text editing keys stay inside the text widgets. The canvas text editor is not an egui widget: the app takes its keys from the frame's egui events before the keymap runs (`app/editor/keys.rs`), its characters and IME from `ShellEvent::TextInput`, and its clipboard from `ShellEvent::Paste` / `CopyRequested`.
* `Esc` closes an open overlay first (`ui.close_overlays`); with the equation editor open it cancels the edit (`text.edit_end` with `commit: false`); otherwise it runs its registered binding (`tool.cancel`).
* `Space` runs `tool.hold`; releasing it runs `tool.release`. Key repeat of the held key does nothing.
* `$cursor` and `$viewport_center` in binding arguments are filled from `FrameInput.pointer` with a world point `[x, y]`, the form the commands take; a key whose placeholder cannot be filled is dropped.
* The UI verbs that have keys (`Mod+O`, `Mod+Shift+S`, `Mod+/`, `?`, `S`, `G`, ...) are `keymap::VERB_BINDINGS`. A test compares the table with the "UI verb" rows of docs/commands.md §6.1 and another checks that no verb key collides with a command key.
* Labels use words on every platform (`Ctrl+Shift+Z`, `Cmd+Shift+Z`, `Opt`, `Left`) because the bundled egui fonts have no glyph for the Mac modifier symbols or the arrows.

## 5. What stays UI-only, and why

| Thing | Why it is not a command |
|---|---|
| Open or closed state of the menu, popovers, dialogs, palette query, hover, scroll, toasts, zen mode, the stats panel, the debug panel | Not session state (docs/commands.md §1.1). |
| Text-field buffers of dialogs (hex colour, room name, LaTeX draft, form values) | A draft until the user applies it; applying runs a command. They live in egui's temporary memory. |
| File and image pickers, clipboard text for the equation editor, links | Need the OS. The UI returns a `HostRequest`; the app does the work and then calls a command (`doc.open`, `doc.save` with `to`, `image.insert`, `library.import`). |
| Pointer gestures on the canvas (drag, resize, rotate, draw, pan, zoom, hover) | The canvas and interaction layer, not this crate. They use the typed gesture API and are listed in docs/exceptions.md. This crate never executes a command per pointer move. |
| The opacity and corner radius slider drags, and the drags of the custom colour picker | A gesture (E13): `gesture.begin`, `update`, `end` with `style.set`; a click is a plain `style.set`. |
| Style choice during a text edit | `style.set` refuses with `text_editing`; the control hands the props to the text editor as `HostRequest::TextEditStyle` (E16), which applies them and passes the result to `text.edit_end`. |
| Opening the context menu and the equation editor | The canvas layer calls `UiState::open_context_menu(screen, world)` (the world point is where `Paste` puts its content) and `UiState::open_equation`. |

## 5a. The touch layout

`Layout` (`widgets.rs`, carried by `Cx`) holds `compact`, `narrow` and the window size; the sizes of targets come from it (`tool_side` 34 or 44, `small_side` 28 or 40, rows 28 or 40, toggles 24 or 36, dialog buttons 32 or 44). `UiState::compact(width)` decides: the preference `LayoutPreference` (`Auto`, `Touch`, `Desktop`, set in the preferences) wins; `Auto` means touch-first (a touch event was seen, or the app called `UiShell::set_touch_first`) or a window narrower than 720 points. The desktop layout is unchanged. The web shell calls `set_touch_first` at start when `(pointer: coarse)` matches. On the touch layout the tool column also keeps clear of the bottom bar (`ChromeRects::centred_panel_height_above_bottom_bar`): on a window 820 points high (an iPad in landscape) the last tools lay under the bar's first buttons before. ## 5b. The library drawer

`surfaces/library.rs` draws the library as a panel that opens from the bottom of the window (`ui.toggle_library`, from the tool column or the menu).

* **Place.** It is as wide as the window less the margins and its bottom edge sits `8` points above the bottom bar and the tab bar, whose rectangles it reads from `ChromeRects` (`bottom_bar`, `tabs`; they are drawn before it, so it follows them if they move) and it records its own there (`library`). Where the tool column (`tools`) reaches down to its height it is narrower by its width, so that its buttons stay free, and its top edge stays under the strip (`strip`, `top_limit`); the toasts, the convert popup, the stats panel and the background popover sit above it (`bottom_floor`, `above_bottom_left`); on a narrow window, where those are collapsed to a button each, it covers them. Its height is 30 % of the window until the person drags the strip on its top edge (the control "Resize the library"); the drag is clamped from 224 points (360 on the touch layout) to 70 % of the window, and what was chosen is `UiState::library_height`.
* **Header.** Title and count ("3 items", or "1 of 3 items" while the search hides some), the search field (it filters by name in the UI, whatever the case), the name for the next Add, Add, Import…, Export and Close. The touch layout makes two rows of it.
* **Sections.** The items are grouped by `library.list`'s `sections`: the person's own items first ("My items"), then one section per imported library, named after its file. A header (`Collapse {name}` / `Expand {name}`; chevron, name, "3 items", or "1 of 3 items" while the search hides some) folds its section on a click (`UiState::library_collapsed`; the tiles of a folded section are not drawn, so none of its pictures is asked for). At its right, rename (`Aa`, not on My items: `library.rename_section` through the rename dialog) and remove (the bin). Removing asks first (a dialog, `UiState::library_remove`) and then runs `library.remove_section`: the library has no undo. A right click on a header opens `Library section menu` (Collapse or Expand, Rename…, Remove section…). The search keeps the matching items of each section, hides the sections with none, and shows the matches of a folded section. A section that is new since the last frame (an import) is scrolled to the top of the list.
* **Tiles.** A wrapping grid in a vertical scroll area, 104 points of picture (112 on the touch layout) and the name under it. A click inserts the item in the middle of the view; a drag onto the canvas inserts it where the pointer is released and shows the picture under the pointer; a release over the drawer cancels. A right click opens a menu built with the menu kit (`Library item menu`: Insert, Rename…, Remove; origin `context_menu`; `UiState::library_menu`) with the same calls as the click and the corner buttons. Rename (`Aa`) and remove (the bin) appear in the corner of the tile under the pointer, and always on the touch layout; they are painted over the tile and take no room in the grid, so hovering moves no tile (`hovering_a_tile_moves_and_resizes_no_tile`). The tooltip shows a larger picture, the name and the element count.
* **Pictures.** `library.thumbnail` (a read, answered with a PNG that has a transparent background) draws an item with the `Renderer` port, the same one `doc.export` uses, so the desktop and the web (WebGPU and the WebGL2 fallback) have it. `thumbs.rs` keeps the answers by item: an entry is good while the item's `content` fingerprint (`library.list`) and the palette (`Palette::of(ctx).dark`, so the dark canvas recolours as it does on the canvas) stay the same, so renaming keeps it and a new drawing or the other theme draws it again. The model reads `library.list` again whenever `Session::library_revision` changes (the library is outside the document, and the app runs an import from its inbox without going through the shell). A tile gets a picture only when it is on screen, and `UiShell::frame` asks for at most two a frame (`thumbs::PER_FRAME`), the larger picture of an open tooltip first; more work left over asks for another frame, and a picture the browser is still drawing (`render_pending`) is asked for again when its renderer wakes the app, without a repaint of its own. Until a picture is there, and when it cannot be drawn (no renderer, an answer that is not a PNG), the tile shows an outline with the item's proportions. At most 200 pictures stay for items off screen; textures are dropped with them.

## 5b2. The versions panel

`surfaces/versions.rs` draws the named versions of the document (`ui.toggle_versions`, the row "Versions" of the File section of the menu and the palette). The data and the rules are `docs/design/versions.md`; this page is the surface.

* **Place.** A card at the top right under the strip. It is 320 points wide, or the window less the margins on a narrow one. Its list scrolls when the window leaves less room than the rows need, and never reaches the bottom bars (`bottom_floor`). The list height is computed before the rows are drawn, so the card has its size in the first frame.
* **Header.** "Versions (3)" and Close, then the button "Name this version…" (the title of `version.save` and an ellipsis). It opens the name dialog (`RenameTarget::NewVersion`), whose Save button is `version.save` and which closes on success (`HostEffect::CompletesRename`). A refusal keeps the dialog open next to its toast. The button is greyed with the refusal of `version.save` as its tooltip (view-only, a room that is still loading).
* **Rows.** Newest first: the name, and under it how long ago and by whom ("5 min ago · Ana"; from a week on the date). The tooltip has the exact UTC time and the number of elements. The time comes from `Model::now_ms`, the session's clock at the last refresh, so a test that moves the fake clock sees the words change. Nothing repaints on a timer: the age updates when something else redraws.
* **Row menu.** A click or a right click on a row opens `Version menu` (the menu kit, origin `context_menu`; `UiState::version_menu`) with the titles of the commands: Open version as copy (`version.open`), Restore version… and Delete version… (each asks first), Rename version… (the rename dialog, `version.rename`). Restore says that the scene goes back, that everything changed since is replaced, that Ctrl+Z takes it back and that every named version stays. Delete says it cannot be undone. The button of the dialog is the command; Cancel runs nothing.
* **Touch.** Rows are at least as tall as a touch target (`row_height` of the layout plus padding, 44 points or more) and stay inside the window; the card narrows to the window.
* **Not built.** A thumbnail of a version (it needs a read command for a version; `library.thumbnail` is for library items).

## 5c. The top strip and its groups

`surfaces/strip.rs` draws one bar across the whole window, flush with its top edge, two control rows tall (72 points on the desktop layout, 96 on a tablet's touch layout; one row, 52 points, on a narrow window). The height depends on the layout only, never on what is selected or drawn, so the canvas never jumps. `surfaces/ribbon/` holds the contextual groups of the strip. They show the properties of the selection, or, with nothing selected, of the tool being drawn with ("new elements": `style.set` writes the defaults, and `tool.set_arrow` the path and heads of new arrows).

* **Place, left to right.** The left cluster: menu and rooms on the first row, the document title under them. The colour group (`topbar.rs`): stroke on the first row and fill on the second, with the same cells in the same order, so they line up column by column: label, the "none" cell ("No stroke" / "No fill", a crossed circle), the six quick colours, the slot of the colour last picked in the colour popover, the eyedropper, the wheel. The last-picked slot is always reserved (empty until a colour is picked), so the wheels never move. The eyedropper (`ui.pick_color`, `eyedropper.rs`, `surfaces/eyedropper.rs`) starts pick mode for that row's colour: a hint under the strip, a crosshair over the canvas, and a swatch with the hex of the pixel under the pointer. The app reads the pixel from the scene texture the shell last drew (`EventCx::sample_scene`, answered by `ShellEvent::Pixel`), so it is the canvas as drawn, pictures included, never the interface. A press and a move ask for the preview and the release picks (so a finger can slide to a colour); the canvas gets none of it. A pick is one `style.set` (one undo step, the defaults when nothing is selected), stores the colour that draws as the pixel in the dark theme (`colors::stored`) and becomes the last-picked swatch. Esc, or the button again, leaves the mode. Where the platform has its own picker (the browser's `EyeDropper`) the verb asks the app for it (`HostRequest::PickScreenColor`) and the browser shows its own loupe. "No stroke" is `style.set` with `stroke_color: transparent`; a "none" cell is greyed with the engine's text (`style.get` `clear_reason`) when the element would show nothing (no stroke on a shape without a fill, no fill on a shape without a stroke, any stroke of a text, arrow, line, pencil stroke or frame, the defaults for new elements). It is greyed and not hidden so the columns stay in place. Then the contextual groups, packed left to right from the colour group, each laid out in the same two rows, with a thin divider (6 points, a hairline, 6 points) between two parts. The "More" button is pinned to the right end. `ChromeRects::strip` is the only rectangle; the menus, the colour popovers, the font popover, the library drawer and the toasts read it.
* **Groups, in this order, never reordered** (first row over second row): stroke (width over style: solid, dashed, dotted); shape (fill pattern, only while there is a fill, over corners: the sharp and round presets, then a radius slider with its value, or `mixed` when the shapes that round differ; a selected picture has them too; for arrows and lines the same controls are in the "More" menu under Corners. A preset is checked only when the radius is exactly its own, so 12 checks neither); arrow (path over the Start and End head buttons, which draw the head of the selected arrow, `style.get`'s `heads`, or the setting of new arrows, and open the head picker: a grid of every head the renderer draws, five to a row, each cell a short shaft with that head, named in its tooltip and accessible name, with the arrow keys moving between cells and past the grid to the "Swap heads" row); brush; font (family dropdown over weight); size (S to XL over bold and italic); text align (left, centre, right over top, middle, bottom for a label or a box); opacity (slider over align and distribute); layering (back, backward, forward, front over flip); actions (duplicate, group, ungroup, lock over edit link, open link, delete). A group is there when `style.get` says its property applies to the selection (for a tool, `ribbon::tool_shows` lists the properties; that table is presentation, the engine skips what does not apply), or when the engine says the command can run: the align row follows `arrange.align`, its distribute buttons `arrange.distribute`. A group with one control row has it on the first row. Layering and the actions need a selection. The width is a row of the stroke group, so it is there only while a stroke applies (a text has none).

* **Groups, in this order, never reordered** (first row over second row): stroke (width over style: solid, dashed, dotted); shape (fill pattern, only while there is a fill, over corners: the sharp and round presets, then a radius slider with its value, or `mixed` when the shapes that round differ; for arrows and lines the same controls are in the "More" menu under Corners. A preset is checked only when the radius is exactly its own, so 12 checks neither); arrow (path over the Start and End head buttons, which draw the head of the selected arrow, `style.get`'s `heads`, or the setting of new arrows, and open the head picker: a grid of every head the renderer draws, five to a row, each cell a short shaft with that head, named in its tooltip and accessible name, with the arrow keys moving between cells and past the grid to the "Swap heads" row); brush; font (family dropdown over weight); size (S to XL over bold and italic); text align (left, centre, right over top, middle, bottom for a label or a box); opacity (slider over align and distribute); image (crop and edit picture over their resets, for one selected image); layering (back, backward, forward, front over flip); actions (duplicate, group, ungroup, lock over edit link, open link, delete). While the paint editor is open the only group is "Edit picture" (the brush, see below the image group). A group is there when `style.get` says its property applies to the selection (for a tool, `ribbon::tool_shows` lists the properties; that table is presentation, the engine skips what does not apply), or when the engine says the command can run: the align row follows `arrange.align`, its distribute buttons `arrange.distribute`. A group with one control row has it on the first row. Layering and the actions need a selection. The width is a row of the stroke group, so it is there only while a stroke applies (a text has none).
* **The highlighter** has no button in the strip. Its icon in the left toolbar is a marker with a bar under it (a neutral grey: half of the icon's ink, so it reads on both themes; the bar is drawn on whole pixels to stay crisp). While the tool is active, the colour group (`topbar::marker_row`) is one row in place of stroke and fill: label, \"none\" (\"No highlight\"), the quick markers (yellow, the default, and the `QUICK_FAMILIES` in shade 400), the slot of the marker last picked, the eyedropper and the wheel. Every control is `tool.set_marker` (tool state; it never writes `style.set`, so no selection, even one made before the tool was chosen, can change, and the stroke colour of new shapes stays as it was). The swatches show the ink the canvas draws the marker with on the current theme (`MarkerColor::rgb`), not the palette colour. The wheel opens the colour popover with the marker target: the same grid (`family_grid`), with the three marker shades 300, 400 and 500 as its rows, every family across, the quick column (none first) and the hex field; there is no custom view, since a colour that is no marker would only be mapped to one. The keys that open the stroke and fill popovers open this one while the tool is active. Any colour is accepted by `tool.set_marker` and mapped to the nearest marker (`MarkerColor::nearest`): `<family>-<shade>` keeps its family, shades below 300 become 300 and shades above 500 become 500; a `#rrggbb` takes the nearest of the 66 markers by RGB distance on the light canvas. \"None\" means a drag removes highlights; Alt does the same for one drag. A highlight is put on a selection with `style.set` `highlight` or `highlight.apply` (commands, the palette, agents); there is no button for it in the strip, and none in the text editor.
* **Nothing selected, a tool that draws nothing** (select, lasso, hand, eraser, laser): only the colour group, which sets the defaults for new elements. The alternative, an empty strip, would change with the tool and hide the controls people use first. The strip keeps its height either way.
* **Controls.** All controls in a row are one height (a small button: 28 or 40 points); no headings, the icons, pictograms and tooltips name the controls (`Corners: Round`, `Fill pattern: Hatch`, `Path: Elbow`, `Path: Auto route`, `Text align: Left`, `Vertical align: Middle`).
* **Fitting** (`ribbon/layout.rs`, `fit`). The widths of the parts are measured in a hidden pass, so the plan is right in the frame it is made. When the groups do not fit the window, the ones at the right end (the least used) go behind the "More" button, whose popover (menu kit, 288 points wide, under the strip, right-aligned with the button) shows them one under the other in their two rows, and under them the properties without a control of their own: sloppiness, pressure, line height, the text box, and the corners of arrows and lines (whose path chips take the place of the corners). The button stays while it has such properties, even when every group fits. When the colour group does not fit beside the left cluster and the button, it collapses to one style button that opens a popover with the same controls (`UiState::style_open`). The last resort is a sideways scroll of everything right of the left cluster. A narrow window (`Layout::narrow`, the phone) has one row: the left cluster, the style button and "More", with every group behind "More" (a scrolling row of 40 point targets on 390 points would show about three of them).
* **Greyed or left out.** A control whose property applies to some of the targets is greyed with the engine's reason. A group the engine says cannot apply at all is left out.
* **State.** `UiState::ribbon_menu` (which menu is open, and its button) is UI-only; Esc and a click outside close it. The opacity slider and the corner radius slider are the two scrubs (E13).

## 5d. The debug panel

`surfaces/debug.rs` draws a card at the top right, under the strip, with the same panel frame, type scale and palette as the others. It opens with the verb `ui.toggle_debug` (`Alt+D`, the row "Debug panel" under View in the main menu, the palette) and with `--perf-overlay` / `?perf=overlay`. A close button in its header runs the same verb. It is a diagnostic, so zen mode does not hide it.

The UI measures nothing. `debug::DebugView` is plain data that the app writes with `UiShell::set_debug` in every frame while `UiState::debug_open` is set (`app/src/debug.rs` builds it, with tests), and `None` when it is closed. Layout: **Frames** (rate, frame time, a graph of the latest frames against the 60 fps line), then sections of name/value rows. A value worth a look (a software rasteriser, a mean frame time over 16.7 ms) gets the warning dot of the collaboration status in front of it, never another text colour. A row that cannot be had is left out or says why; nothing is shown as 0 that was not measured.

| Row | Source | Cost and limits |
|---|---|---|
| Rate, Frame time, graph | the shell times each frame from the start of the egui pass to the end of present (`FrameOutput::stats`, `profile::FrameMeter`); frames in the last second, mean and worst CPU time, the latest 90 frames | two clock reads per frame, only while open. A quiet canvas shows `idle (draws on demand)` and the last frame with its age, not 0 fps. The frame time is the frame without the panel: its refresh frames are not counted, and on every other frame the panel's own cost is taken out (see the next row) |
| UI, Canvas scene, Render, Present | the parts of a counted frame (`profile::Stage`): the egui pass without the scene build and the panel, the scene build (`App::paint_canvas`), the CPU side of the Vello run, tessellation and present without the panel's share | means over the last second. A part a shell does not run is left out (a windowless shell has no render and no present). Present includes whatever the driver waits for; they do not add up to the frame time exactly, the rest is platform output and clipboard work |
| Debug panel | the panel's own cost per frame: building its content, laying it out and painting it, tessellating its shapes (`FrameResult::debug`, `AppTimes`) | `x ms, not counted`. A mean of the last second, with the refresh frames in it; the number is what was taken out of the frame time. The GPU time row cannot be split in the same way: the composite pass has no finer timestamps |
| Renderer, Adapter, API, Device, Driver, Draws on | `RendererInfo` from the wgpu adapter info (native, WebGPU) or the WebGL2 `RENDERER` and `VENDOR` strings | static. A browser reports little: empty fields say `not reported`. `Draws on` is `CPU (software driver)` for llvmpipe, lavapipe, SwiftShader, WARP, with the warning dot |
| GPU time | timestamp queries around the composite pass (the blit of the Vello image and egui), resolved into a buffer and read a frame later without waiting | native only, and only on a device that has `TIMESTAMP_QUERY`; else `not available here`. Vello's own compute passes are not timed: Vello 0.11 submits them itself and has no hook outside its profiler feature |
| GPU memory, Reserved | `Device::generate_allocator_report` totals, refreshed twice a second | `None` on the web, WebGL and drivers without an allocator report: the rows are left out |
| Elements, Visible, Drawn, Cache, Zoom | the last `FrameReport` of the scene composer and the camera | Cache is hits and misses of the last scene build, not totals |
| Redraw reason, Canvas, Collaboration | the reason of the frame, the surface size and scale, `collab.status` | |

Zero cost when closed: no view is built, the shell and the back end measure nothing (`Backend::set_stats(false)` leaves the query set unused), and no timer exists. Open, the panel redraws itself twice a second with the redraw reason `debug_panel` (`performance.md` section 2.3), so an idle canvas with the panel open is not idle on purpose; the numbers it shows are what they are because of that, and the refresh frames are left out of them. The content (`DebugView`) is built at that refresh and kept between; the card itself is laid out in every frame, because egui is immediate mode and a card that replayed stored shapes would drop its widgets, the hover tooltips of long values and their accessibility nodes (measured: replaying could save at most about 0.07 ms a frame in a release build, the content of the card without its header).

## 5e. The minimap

`surfaces/minimap.rs` draws a small card at the bottom right: the whole drawing in outline, and the part of it the window shows as a tinted rectangle in the accent colour. It is off by default. The setting `view.minimap` holds the choice, so it is kept between runs like the other settings; `settings.toggle` with `key: view.minimap` (`Alt+M`, "Minimap" under View in the main menu and in the context menu's View flyout, the palette, a switch in the preferences) flips it, as it does the snap and attach switches; the rows show the setting as checked. Miro's `M` key is the math tool here, hence `Alt+M`.

* **What other tools do.** tldraw draws the shapes' bounds on a canvas in the corner and fits the union of the page and the viewport; a drag moves the camera and a click centres it. Miro has it at the bottom right, in the zoom menu, with an `M` key. draw.io has a floating Outline window with the viewport rectangle to drag. FigJam has none. This one follows tldraw: the extent is the content together with the camera's rectangle, so the rectangle never leaves the card.
* **Place.** `ChromeRects::lift_bottom_right` puts it at the window margin, or above the bottom bar, the tab bar or the library drawer when one of them reaches under it (a narrow window, many tabs, the open drawer). It records its rectangle (`ChromeRects::minimap`); the presence panel, which also sits at the bottom right, stands above it. Zen mode hides it with the rest of the chrome. The debug panel is at the top right and the tool column at the left, so they do not meet it unless the window is very short. The card is 188 by 124 points, 208 by 140 on the touch layout (a finger aims at it) and 132 by 88 on a phone.
* **Data.** `crate::minimap::Scene` (kept in `Model::minimap`, a `Snapshot`) is the document reduced to one `Mark` per element: the axis-aligned bounds of the rotated box and a look. A shape with a fill is a filled box in that colour; a shape or frame without one is a 1 point outline, so what it holds stays visible; a line or arrow is the segment from its first to its last point; text, formulas and pen strokes are a box of their colour at 55 % strength; a picture is grey. The opacity of the element is kept, and both theme colours (`Color::for_dark_theme`, as the canvas draws) are worked out when the scene is built, so a frame converts nothing. A text bound to a shape is left out. A mark under 1.5 points is grown to a dot.
* **Cost.** Off: nothing is read, built or drawn (`Snapshot::sync` drops what it had), and the card's code is not reached. On: the model reads the camera every frame (a few numbers), and builds the scene again only when the tab or the version of its elements changed (`Stamp`), which is one pass over the live elements; a frame draws at most `MAX_MARKS` rectangles and lines, never the scene. A document with more than 2,048 elements is merged into a 48 by 32 grid first (the topmost element of a cell gives it its colour); the elements bigger than a few cells (frames, backgrounds) are kept as they are, up to 512, so the work of a frame has an upper bound whatever the size of the document. While a gesture runs, the scene of a document that was merged is not rebuilt (it catches up after the gesture), because a drag changes the document every frame. Measured in a release build (`cargo test -p drafftink-ui --release --test minimap -- --ignored --nocapture`), draw and tessellate of the whole UI at 1,000 elements: 273 µs with the minimap off, 508 µs on, so the minimap adds about 235 µs a frame (the card alone, with no elements, 6 µs); the model's refresh after a document change goes from 90 to 178 µs; building the scene of 100,000 elements takes 22 ms and leaves 1,536 marks to draw. A frame that is not drawn (idle) costs nothing: the minimap asks for no repaint.
* **Camera.** The card draws the camera the app reports with `UiShell::set_live_camera` (the interaction layer's, which runs ahead of the session's while a pan or zoom goes on, until `view.set` catches up every 100 ms), else the session's. The app reports it only while the setting is on.
* **Input.** A press on the card centres the view on that point; a press inside the rectangle keeps its place under the pointer (no jump), and a drag moves it. Each change is one `view.set` with the `scroll` the pointer asks for, the same quiet camera command a pan ends with (`RingMode::Quiet`: no ring entry), so there is no exception row: nothing but a command moves the camera. The mapping of the card is the one at the press for the whole drag (`Grab`), because the extent grows with the rectangle and a mapping that followed it would slide the picture under the pointer; the pointer is held on the card's edge when it leaves. The wheel (and a pinch, or Ctrl+wheel) over the card is `view.zoom_at` about the middle of the window, `e^(0.002 * points)` a frame, at most 2 times. The press is read from the raw pointer state, so a tap that starts and ends inside one frame (touch) still moves the view. The canvas ignores a pointer that egui owns, so nothing reaches the tools.
* **Accessible name.** The card is a node named "Minimap".
* **Tests.** `tests/minimap.rs` (the card, the places, the input, the toggle, the key, the rows), `crate::minimap` and `chrome` unit tests (the maths, the merge, the lift), `engine/src/cmd/settings_tests.rs` (the setting survives a restart).

## 5f. The colour popover and its two views

`surfaces/color.rs` draws the popover of the stroke, the fill and the page colour. A switch under its title chooses the view, and the choice is the setting `ui.color_picker` (`swatches` by default, or `custom`), so it is kept like the other settings and every popover opens in the view the person last chose. The two buttons are `settings.set` calls (`Colour picker: Swatches`, `Colour picker: Custom`); the popover stays open when one is pressed.

* **Swatches** is the grid of 22 families by 11 shades, the quick column and the hex field (section 3, "Colours the UI shows").
* **Custom** (`surfaces/color/custom.rs`) is one saturation and value square (saturation across, value up), a hue bar and, for the stroke and the fill, an alpha bar. Under them are a chip with the colour, the hex field and the "None" cell. The page colour has no alpha bar: it is a solid colour, and "None" is its clear choice. The brush colour of the paint editor (`ColorTarget::Brush`) has no alpha bar either (the brush has its own opacity) and no "None" cell; its drag shows in the popover and one `image.paint_brush` runs at the release, as the page colour does, and it is not mapped for the dark theme (below). Text colours are the stroke colour, so the stroke popover is the text colour picker too.
* **The model** is `hsv::Hsv` (hue in degrees, saturation, value) plus an alpha byte, so a hue chosen on the bar survives a trip to a grey or to black, which a conversion through RGB would lose. `Hsv::from_color` and `to_color` are the conversion; a test walks a lattice of the RGB cube and every grey and checks the round trip.
* **The hex field is kept in step.** It shows the colour as the canvas draws it and follows the picker, and a colour set from outside (a swatch, an undo, another selection) moves the picker. While the field is being typed in, or shows the error of a refused value, it is left alone. Enter applies a typed colour and the custom view stays open.
* **Dark theme.** (Not for the brush: it stores what it shows.) The square and the bars show displayed colours, and a pick stores the colour whose display it is (`colors::stored`, `Color::from_dark_theme`), as the hex field and the eyedropper do. A colour the filter cannot show is stored as the nearest one it can, and the chip and the hex field show that one.
* **A drag is one gesture** (E13). The three widgets of a colour share the gesture `ScrubControl::StrokeColor` or `FillColor` through `scrub::drive`: `begin` at the first change, `update` for each further one, `end` at the release, so the canvas previews the colour live and one undo step undoes the whole drag. A drag that starts on the square may go on over the bars. Esc cancels it. An arrow key on a focused widget (1 per cent, 10 with Shift) is a plain `style.set`. The page colour has no gesture command: its drag is shown in the popover and one `doc.set_background` runs at the release.
* **Touch.** The square is 180 points tall instead of 150, the bars 28 instead of 16 and the handles 12 instead of 8 points in radius (the toggles of the switch use the touch heights of the layout).
* **Names.** The widgets are sliders named `Saturation and value`, `Hue` and `Alpha` (the ribbon's slider is `Opacity`).

**What other tools do.** Excalidraw's popover is a swatch picker: top picks, a base colour and its shades, a hex field and an eyedropper; it has no continuous picker, and a typed colour joins a list of custom colours. tldraw offers only its fixed palette in the style panel. Figma's colour picker has a Custom tab with a saturation and brightness square, a hue slider, an alpha slider, a hex field and an eyedropper, next to the libraries. This popover follows Figma for the custom view and keeps Excalidraw's swatches as the default.

## 6. Repaints

The UI requests a repaint only for work that exists: one extra frame after commands ran (the model changed), and toasts (`request_repaint_after` until the fade starts, then 30 Hz during the 0.6 s fade; none afterwards). egui's own animation of a newly opened area and the text caret blink are egui's requests. `tests/frame.rs` checks that a quiet frame asks for no repaint.

## 7. For the app

```rust
let mut shell = UiShell::new(is_mac);            // once
shell.set_collab(view);                          // when the collab client changes
let res = shell.frame(ui, &mut session, FrameInput { pointer });   // every egui pass
for r in res.report.host { /* open a picker, copy text, ... then call a command */ }
```

Things the app does for the surfaces of this work:

* `HostRequest::PickLibraryImport`: show a file picker for an `.excalidrawlib` and call `library.import` with `mode: merge` (the library panel's Import button; `PickLibrary` opens a library as a tab instead).
* `HostRequest::PickSaveTarget` now follows the Save As name dialog: the document is already renamed, so the picker should suggest `<name>.json` or the like and then call `doc.save` with `to`.
* Collaboration: `Peer` has two new fields, `id` (the `peers[].id` of `collab.status`, which `collab.follow` takes) and `followed`. `CollabView::from_status(&collab.status output)` builds the whole view, so the app can replace `collab_view_of` with `CollabView::from_status(&session.query("collab.status", json!({}))?)`.
* Export and the library export write with `to: {download: name}`; the app's files port saves the bytes (native: the downloads folder; web: a download).
* Touch: call `UiShell::set_touch_first(true)` on a touch-first device (web: `matchMedia("(pointer: coarse)")`). Touch events seen by egui set it too.
* The layout preference lives in `UiShell.state.layout` and is not stored; persist it if wanted.
* For the canvas overlay: `Model.selection` has the id, kind, link, frame and label of each selected element (the first 50), and `Model.selection_link` the link of a single selection. The link icons of unselected elements are `InteractionOverlay::link_icons` (render's job).

Pointer events go to the canvas only when `!res.modal` and egui does not own the pointer. The GPU shell should install the egui context's theme through `UiShell` only (it applies the `theme` setting itself). Install fonts happens inside `draw` (`theme::ensure_fonts`).

## 9. Open points

* Search results show the text, the kind and the first page (100) of `element.query`; there is no paging control.
* The stats panel reads the bounds of the selection with `selection.get` (through `Session::query`, so no ring entry) and edits them with `element.set_bounds`, one value at a time. A rotated selection shows the bounds `selection.get` reports.
* The height the person drags the library drawer to is kept in `UiState::library_height` for the session and is not stored; an app that wants it between runs reads and writes the field, as for the layout preference.
* The first picture on the desktop opens the app's offscreen GPU device on the UI thread, which can take a moment; the pictures after it are drawn two a frame.
* The auto-resize buttons say Fit to text and Fixed width but do not show the current state: no query reports it.
* The menu, the context menu and the palette no longer wait for commands: every catalog command is registered.
* Touch: the touch layout is built (section 5a) and tested headless at iPad and iPhone sizes, also with safe-area insets (`ui/tests/touch_layout.rs`); no real tablet or phone has run it. The canvas gestures are the canvas layer's.
